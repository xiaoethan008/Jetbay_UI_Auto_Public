# 测试策略与质量门禁

本文件回答“怎样算测够、怎样算可以进入发布判断”。它是长期规则；每个版本的具体覆盖情况放到对应版本的 `需求追溯矩阵`。

## 测试分层

| 层级 | 类型 | 覆盖对象 | 本项目示例 | 目标 |
| --- | --- | --- | --- | --- |
| L1 | 规则 / 单元 | 纯逻辑、排序、过滤、错误页识别 | `tests/test_empty_leg_recommendation_rules.py`、`tests/test_error_page_detection.py` | 单个规则是对的 |
| L2 | 集成 / 数据 | 接口、DB、Excel、数据源对比 | `scripts/compare_world_cup_routes_excel.py`、`scripts/compare_popular_aircraft_with_db.py` | 数据来源和页面抽取能对上 |
| L3 | Contract / SEO | 字段结构、SEO 标签、hreflang、redirect、Heading 规范 | `scripts/seo_canonical_hreflang_scan.py`、`scripts/check_content_heading_styles.py` | 字段、标签和规范是对的 |
| L4 | UI E2E | 用户真实路径、弹窗、表单、地区切换、视觉可见性 | `tests/test_*.py` Playwright 用例 | 用户能走通，关键 UI 可见可用 |

## 用例拆分原则

每条用例只覆盖一个“可独立失败的点”。如果失败后无法直接判断坏在哪里，就应该拆分。

| 来源 | 拆分方法 | 示例 |
| --- | --- | --- |
| 主路径 | 每个核心用户路径至少 1 条 | 登录成功、Contact Us 打开、世界杯表单正常提交 |
| 异常路径 | 每种独立错误原因 1 条 | 邮箱格式错误、协议未勾选、登录过期提交 |
| 状态组合 | 每个关键状态 1 条 | 未登录、已登录、token 失效、地区切换后 |
| 数据源 | 每类数据源 1 条 | Excel 对比、DB 对比、API response 对比 |
| 视觉风险 | 每个动态布局风险 1 条 | Multi-City 三段航程 CTA 不被裁切 |
| SEO 规则 | 每类 SEO 规则 1 条 | hreflang、robots、301 redirect、Heading 字号 |

## 问题清单记录规则

- 记录任何 Bug 或疑似问题时，必须标出关联测试用例，至少包含用例标题和自动化 `nodeid`；如能匹配到 `artifacts/测试用例清单.csv`，同时写入用例 ID。
- 记录任何 Bug 或疑似问题时，必须写操作步骤；优先使用测试用例清单中的“测试步骤”，如未匹配到用例清单，则根据自动化脚本实际动作补全可执行步骤。
- 问题清单必须按状态分区排序：`未修复/部分修复` 放在最上方，`待确认/环境阻塞` 放在中间，`已修复并复测通过` 放在最下方。
- 问题修复后只移动到清单底部并追加修复版本、复测时间和证据，不删除问题，不覆盖首次发现时的步骤、实际结果、根因和证据。

## 发布判断规则

- P0 需求无用例覆盖：不能发布。
- P1 需求无用例覆盖：原则上不能发布，除非用户明确确认风险。
- 自动化失败：必须判断是产品缺陷、脚本维护问题还是环境限制。
- 问题清单中的 P0/P1 未修复：不能直接发布，除非有书面风险确认。
- 需求变更导致用例不再适用：用例和矩阵标记“需求变更跳过”，不得当作失败。
- 新需求与历史继承规则冲突：默认按历史规则继续验收，并在问题清单中记录“文档冲突/需求遗漏”或“待确认”；只有产品明确确认覆盖旧规则时，才改按新需求验收。
- 环境未配置导致无法执行：矩阵标记“环境限制”，并说明是否需要在 prod/staging 补测。
- 版本收尾前，必须回看本轮问题清单、待确认项、未测/阻塞项和用户确认口径；如有后续版本仍需继承的规则，先补 `历史继承规则.md`，再宣布版本测试完成。

## 开发前适用规则

当“代码还没写，但测试用例已经定了”时，先完成：

1. 从需求文档拆 AC / 验收点。
2. 对照 `历史继承规则.md` 检查新需求是否冲突，冲突项先标记文档冲突/待确认。
3. 每个 AC 至少落到一条 TC 或一个专项脚本。
4. 新增专项脚本前先确认是否长期纳入回归；一次性专项只记录执行证据，不写入固定回归清单。
5. 建立版本 `需求追溯矩阵`，标记哪些是 P0/P1。
6. 若有接口、DB、Excel、SEO 规则，提前定义 L2/L3 校验方式。
7. 开发完成后先按矩阵补齐“覆盖状态”，再执行回归。

## 版本收尾规则

每次版本测试结束前，必须执行一次“长期规则筛选”：

1. 读取本版本问题清单、待确认项、未测/阻塞项和需求追溯矩阵。
2. 找出用户/产品明确确认、后续版本仍会影响验收的问题分类、品牌词、文案、SEO、数据或环境规则。
3. 将需要继承的规则补到 `历史继承规则.md`，或更新已有规则状态。
4. 若规则可自动化，补到固定回归或专项脚本索引；若不可自动化，说明人工检查方式。
5. 若本轮没有新增继承规则，在版本总结中写明“本轮无新增历史继承规则”。

## 变更影响分析

每个版本开测前，代码改动和需求变更都要映射到测试范围：

| 改动类型 | 必看风险 |
| --- | --- |
| Header / Footer / 公共组件 | 全站入口、Contact Us、移动端导航、多语言 |
| 表单 | 必填、格式、协议、重复提交、登录过期、成功页 |
| 数据模块 | 默认地区、地区切换、Excel/DB/API 对比、无数据状态 |
| SEO | meta、robots、hreflang、redirect、sitemap、Heading、Alt |
| 视觉布局 | 桌面/移动、动态高度、弹窗底部按钮、轮播多帧 |
| 路由 / sitemap | 404、301、站内链接、废弃 URL |
