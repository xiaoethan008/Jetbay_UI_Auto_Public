# 需求追溯矩阵规范

本文件回答“有没有遗漏”。矩阵不是问题清单，也不是测试报告；它用于把需求、页面模块、数据源、测试用例和自动化脚本对账。

## 存放位置

每个版本单独维护一份：

```text
artifacts/
  官网Vx.x.x（模块名）/
    需求分析/
      需求追溯矩阵_Vx.x.x.csv
      需求追溯矩阵_Vx.x.x.md
```

CSV 用于筛选和统计，MD 用于快速阅读。

## 字段定义

| 字段 | 说明 |
| --- | --- |
| 需求ID | 版本内唯一，例如 `V403-REQ-001` |
| 版本 | 例如 `V4.0.3` |
| 需求来源 | PRD、Excel、DB、SEO BRD、历史问题、用户补充等 |
| 页面/模块 | 被测页面或业务模块 |
| 需求点/AC | 可验证的验收点 |
| 优先级 | P0 / P1 / P2 |
| 类型 | 功能 / 异常 / 权限 / 数据 / SEO / 视觉 / 回归 |
| 数据源/API/DB | 关联接口、数据库表、Excel 或无 |
| 继承规则 | 关联 `历史继承规则.md` 中的规则 ID，例如 `INHERIT-BRAND-001` |
| 是否被本版本覆盖 | 是 / 否 / 待确认；用于判断新版需求是否明确覆盖历史规则 |
| 冲突判断 | 无冲突 / 文档冲突 / 截图冲突 / 代码实现冲突 |
| 处理口径 | 按历史规则验收 / 按新需求验收 / 待产品确认 |
| 关联用例ID | `artifacts/测试用例清单.csv` 中的 TC-ID |
| 自动化脚本 | 关联 `tests/` 或 `scripts/` |
| 覆盖层级 | L1 / L2 / L3 / L4，可多选 |
| 覆盖状态 | 已覆盖 / 部分覆盖 / 待补 / 需求变更跳过 / 环境限制 |
| 问题清单/证据 | 关联问题清单、截图、报告 |
| 备注 | 风险、跳过原因、待确认事项 |

## 覆盖状态规则

| 状态 | 使用条件 |
| --- | --- |
| 已覆盖 | 至少有一条可执行 TC 或脚本，且预期可验证 |
| 部分覆盖 | 主路径覆盖了，但异常、边界、地区、数据源或移动端未全覆盖 |
| 待补 | 需求存在，但没有对应 TC / 脚本 / 人工检查说明 |
| 一次性专项 | 只按用户指定场景单独执行，不纳入固定全量回归 |
| 需求变更跳过 | 需求删除或用户确认不测 |
| 文档冲突 | 最新需求文档、截图、表格或注释与历史继承规则/同文档其它来源冲突 |
| 环境限制 | 当前环境不具备能力，例如 dev 未启用 canonical |

## 门禁规则

- P0 行不得为“待补”。
- P1 行不得长期为“待补”；若暂不覆盖，需要在备注写明风险确认。
- 每个数据模块必须能追溯到 Excel、DB、API 或需求文档中的至少一个来源。
- 每个表单模块必须覆盖登录态、必填、格式、协议、提交反馈中的适用项。
- 每个 SEO 模块必须写明环境开关，避免把 dev 未配置能力误报为缺陷。
- 一次性专项脚本不得默认进入全量回归；后续复用前需重新确认是否升级为固定回归能力。
- 新版本需求与 `历史继承规则.md` 冲突时，必须在矩阵中标记“文档冲突/待确认”，不得只按新文档字面值生成预期。

## 新版本操作流程

1. 复制上一版本矩阵或按模板新建。
2. 读取 `历史继承规则.md`，把适用规则写入矩阵，并先检查新需求是否冲突。
3. 根据最新需求文档补需求行。
4. 根据 dev 分支代码改动分析补风险行。
5. 把每行需求映射到 TC-ID、脚本或人工检查。
6. 执行测试后更新覆盖状态和问题清单链接。
7. 发布评审前过滤 P0/P1 的“待补”行。
